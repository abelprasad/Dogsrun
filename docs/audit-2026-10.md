# DOGSRUN Code Audit — October 2026

Full read of `src/`, `tests/`, `scripts/`, config and docs. Covers correctness, security, data integrity and code health. UX/visual issues are already in [`ux-audit-2026-07.md`](./ux-audit-2026-07.md) and are not repeated. System reference: [`ARCHITECTURE.md`](./ARCHITECTURE.md).

Baseline on 2026-10-04: `tsc` clean, `eslint` clean, `matching.test.ts` passes. `npm audit`: 16 vulnerabilities (1 critical, in `next`).

**Verify** = depends on Supabase config (RLS, auth settings) that isn't in the repo, so I couldn't confirm it from code.

---

## High

### H1. `npm run seed` emails real rescues about fake dogs
`scripts/seed-test.ts:113-135` creates an **approved, non-`is_test`** shelter, inserts a Labrador in PA, then calls `/api/alerts`. `api/alerts/route.ts:128-131` only skips test *rescues* and test *shelters*, so every real approved rescue whose criteria accept that dog (any PA rescue with an empty breed list, for example) gets a real alert email and alert row for "[TEST] Buddy". The dog also appears on public `/dogs` while the script runs. `api-security.spec.ts` creates its orgs the same way.
The seed also writes `max_age_years`/`max_weight_lbs` (`:141-142`), columns the current criteria model no longer uses, so it may simply fail.
**Fix:** set `is_test: true` on every org the seed and specs create. Longer term, add a separate Supabase project for tests, since right now tests run against production.

### H2. `GET /api/respond` changes state with no authentication
`api/respond/route.ts:13-82`. The alert email's "Interested" link is a plain GET that updates the alert and emails the shelter. Problems:
- Corporate mail scanners (Outlook Safe Links, Mimecast, etc.) pre-fetch links, which marks the rescue as "interested" and emails the shelter before a human clicks anything.
- It isn't idempotent: every hit sends the shelter another "interested" email.
- Anyone with an alert id can flip its status. There is no token.
- It always redirects to `/responded` ("You're Interested"), even for `action=pass`.

**Fix:** make the GET render a confirm page with a POST button. Sign the link (HMAC of `alert_id` + action) or store a per-alert token. Skip the email when the status was already `responded`.

### H3. Every email failure is silently ignored
Resend 6 never throws. `emails.send()` returns `{ data, error }` (confirmed in `node_modules/resend/dist/index.mjs`), and none of the 9 call sites check `error`. Effects:
- `/api/contact` tells the user "sent" when nothing was sent.
- `/api/alerts` counts a match as "sent" (`:258`) and leaves an `alerts` row saying `sent` for an email that never went out. Because the rescue is now "already alerted", **Resend Alerts will never retry it.**
- SOP step "check Sentry for errors in /api/alerts" can't work, because nothing is thrown.

**Fix:** a small `sendEmail()` in `lib/` that throws (or `Sentry.captureException`s) on `error`. Use it everywhere. In `/api/alerts`, delete the alert row or mark it `failed` if the send fails.

### H4. Unapproved shelters can publish dogs to the public site
- `dashboard/dogs/new/page.tsx:8` checks `type === 'shelter'` but not `approval_status`. Only `/dashboard` itself shows the ApprovalWall.
- `new-dog-form.tsx:69` inserts with the browser client, so the only gate is RLS. **Verify** whether the `dogs` insert policy checks approval.
- `(public)/dogs/page.tsx:96-100` filters `is_test` only, not shelter `approval_status` or `is_active`. `(public)/dogs/[id]/page.tsx:15-20` doesn't filter `is_test` either.

So a pending or rejected registrant (anyone who uploads any PDF) can list dogs on dogsrun.org. Alerts are blocked for them; public listing isn't.
**Fix:** check approval in the shared dashboard layout (or a helper) for every shelter/rescue page. Move dog creation to an API route (also required by CLAUDE.md's "all writes through API routes" rule). Add `.eq('organizations.approval_status','approved')` to both public queries.

### H5. "Deactivate org" does nothing
Admins can toggle `organizations.is_active` (`api/admin/orgs/route.ts`), but nothing reads it. A deactivated rescue still gets alerts (`api/alerts/route.ts:128-131` checks approval and `is_test` only), a deactivated shelter's dogs stay public, and both can still log in and use the dashboard. (The `is_active` filters in alerts and the browse page are on `rescue_criteria.is_active`, which is a different column.)
**Fix:** treat `is_active = false` like not approved: skip it in matching and digests, hide it publicly, and show the ApprovalWall.

### H6. `next@16.2.4` has a critical advisory, including a proxy bypass
`npm audit` reports a Server Components DoS and "Middleware / Proxy bypass in App Router applications via segment-prefetch routes". `proxy.ts` is the only gate on `/dashboard` for anonymous users. Pages re-check auth, which limits the damage, but this should still be patched. **Fix:** `npm i next@latest eslint-config-next@latest`, then `npm audit fix` for the transitive ones (sharp, ws, postcss, @sentry → @opentelemetry).

## Medium

### M1. `admin/page.tsx` reads everything with the service role and has no auth check of its own
It relies entirely on `admin/layout.tsx`. Next's docs warn that layouts don't re-run on every navigation and that auth checks belong next to the data. Combined with H6, this is the most valuable page in the app (every org's email, every dog). **Fix:** one `await requireAdmin()` at the top of the page. The same helper also removes the 7 copies of the admin check across API routes.

### M2. Dogs with no state are alerted to every rescue in the country
`matching.ts:69-71`: `!dog.state` → match. State is optional on the intake form, so a shelter that skips it sends the dog to rescues in every state, ignoring `states_served`. **Fix:** fall back to the shelter's `organizations.state` (always set at registration) when `dog.state` is empty, in both `/api/alerts` and the digests.

### M3. Digests skip urgent dogs and include dogs that shouldn't be there
`approve/route.ts:138` and `digest/route.ts:76` select `status = 'available'` only. **`urgent` dogs, the ones that most need a rescue, are never in a digest.** They also don't filter test or unapproved shelters, unlike `/api/alerts`. **Fix:** `.in('status', ['available','urgent'])` plus the same org filters as `/api/alerts`, ideally by extracting the "eligible dogs × rescue" query into `lib/matching.ts` once (issue #20).

### M4. HTML injection in digest emails
`approve/route.ts:174-175` and `digest/route.ts:116-117` interpolate `dog.sex` and `dog.state` without `escapeHtml`. Because dogs are inserted from the browser (H4) with no server validation, both are attacker-controlled strings. This violates the CLAUDE.md escaping rule. **Fix:** escape them. The real fix is the server-side dog-create route from H4, with sex/state validated against `VALID_SEXES`/`US_STATES`.

### M5. `/auth/confirm` looks up the org by email
`auth/confirm/route.ts:26-30` uses `.eq('email', user.email)`. This is the exact pattern CLAUDE.md forbids. If an org's email differs from the auth email, it routes a rescue to the shelter dashboard. **Fix:** `.eq('id', user.id)`, or just redirect to `dashboardPathFor(...)`.

### M6. Rescues get 404s on dogs they were matched with
`dashboard/rescue/page.tsx:96` links "View Profile" to the public `/dogs/[id]`, which 404s unless status is `available`/`urgent`. As soon as a shelter marks a matched dog `pending` or `rescue_requested`, the rescue can't see it. `/dashboard/dogs/[id]` already has the correct rescue-has-alert access rule. **Fix:** link there instead.

### M7. Euthanasia countdown is off by the user's UTC offset
`euthanasia-countdown.tsx:7`, `status-badge.tsx:12`, `dogs-table.tsx:84`: `new Date('2026-10-05')` is midnight **UTC**, which is 8pm ET the previous evening. Dogs show "Past Due" and "Critical" hours early, and the countdown is wrong for every US user. `new-dog-form.tsx:193` also computes `min` date in UTC, so after ~8pm ET you can't pick today. **Fix:** decide what the date means (end of day local to the shelter) and parse it that way in one helper.

### M8. Breed matching misses obvious matches
The breed list (`breed-select.tsx`) has near-duplicates: `German Shepherd`/`German Shepherd Dog`, `Malinois`/`Belgian Malinois`, `Husky`/`Siberian Husky`, plus `X mix` variants. Matching is "criteria string is a substring of the dog breed", so criteria `German Shepherd Dog` does **not** match a dog entered as `German Shepherd`, and criteria `Labrador Retriever mix` doesn't match `Labrador Retriever` with `mix = true`. **Fix:** collapse the list to one canonical name per breed, drop the `mix` variants (the checkbox already covers that), and normalize existing rows.

### M9. Registration can strand a user permanently
`register/page.tsx:70-124`. If anything fails after `signUp` (upload, rate limit, API error), the auth user exists with no org. Retrying `/register` returns "User already registered", and logging in redirects back to `/register` (`dashboardPathFor`). There's no way out without an admin. The flow also sends two emails: the signup confirmation and then a magic link (`:128`). **Fix:** when `signUp` reports an existing user, sign in instead and continue to the upload/register steps. Drop the extra OTP email.

### M10. The root layout puts the public navbar on every route
`app/layout.tsx:30` renders `<Navbar/>` + footer around dashboard, admin and auth pages. That contradicts CLAUDE.md ("root layout is a minimal shell only"; `(public)/layout.tsx` is an empty fragment). Consequences:
- Admin has two `sticky top-0 z-50` bars fighting for the same spot. Dog profile/edit pages show three nav bars (public navbar, DashboardNav, page sub-nav with a second Sign Out).
- `Navbar` calls `getAuthContext()` (an Auth network round trip plus 2 queries). That makes **every public page dynamic and uncacheable**, and the dashboard layout repeats the same calls.
- The root layout doesn't re-render on client navigation, so after login (`router.push`) the navbar keeps showing "Login / Register" until a hard reload.

**Fix:** move Navbar + footer into `(public)/layout.tsx`, which matches the documented architecture.

### M11. Schema and RLS aren't versioned
No migrations or policies are in the repo, yet RLS is the only protection for browser-client writes: dog insert, criteria upsert, and `tax-docs` upload with `upsert: true` (`register/page.tsx:88`). That upload happens before email confirmation, so it may run as `anon`. **Verify** that anon can't overwrite `tax-docs/{other uid}/501c3.pdf`. **Fix:** `supabase db pull` into `supabase/migrations/` so policies get reviewed like code.

### M12. Admin identity is an email string match
`auth-context.ts:29` and 6 API routes check `admins.email = user.email`, which is case-sensitive. The SOP says to insert the admin email *before* inviting. If Supabase "Confirm email" is ever off, whoever signs up with that address first becomes admin. **Verify** that email confirmation is on. **Fix:** compare `lower(email)`, or better, store `user_id` in `admins` after the invite is accepted.

### M13. Editing a dog never re-triggers matching (answers issue #14)
`/api/dogs/update` doesn't call matching. Reverting `pending → available` or fixing a typo'd breed or state alerts nobody new until someone presses "Resend Alerts". Adding a euthanasia date sends no "now urgent" notice to rescues that were already alerted. Saving rescue criteria also doesn't match existing dogs (issue #13). The SOP says it does ("matching happens automatically the moment … a rescue sets their criteria"), which is wrong.

## Low

- **L1.** `dashboard/page.tsx:26`: `.in('status', ['available', null])` never matches NULL in SQL, so the "Available" stat misses null-status dogs. Use `.or('status.eq.available,status.is.null')`.
- **L2.** `dashboard/dogs/[id]/page.tsx:115` types `color` as `string`, but it's `string[]`, so it renders "BlackWhite". Join it like the public page does.
- **L3.** `breed-select.tsx:125` says "press Enter to use", but Enter submits the surrounding form. In `criteria-form.tsx` that saves the criteria instead of adding the breed.
- **L4.** `/auth/login` ignores the `?redirect=` that `proxy.ts` sets, so deep links from emails (e.g. "View all matches") land on the welcome page.
- **L5.** `/auth/update-password` shows "Verifying your reset link…" forever for an expired or invalid link (`:58`). Add a timeout and an error state.
- **L6.** `resend-alerts-button.tsx:19` shows `data.message || 'Done'`, so 403/500 responses show "Done".
- **L7.** `api/dogs/update/route.ts:92,99`: `updates.age_years ? … : null` turns age `0` into null. `matching.ts:58` also treats age 0 as unknown.
- **L8.** Raw DB/library errors go back to clients: `api/register:90`, `api/contact:56`, `api/dogs/update:116`, admin routes.
- **L9.** `ratelimit.ts:7`: if Upstash env vars go missing in production, rate limiting silently turns into allow-all. Log or warn when `NODE_ENV === 'production'`.
- **L10.** `admin/page.tsx:13-15` loads all orgs, dogs and alerts. PostgREST caps responses at 1000 rows by default, so totals and response rate will silently become wrong past that point. Use `count: 'exact', head: true` for stats.
- **L11.** `globals.css:18` forces `font-family: Arial` on body, so the Geist fonts loaded in `layout.tsx` are downloaded and never used.
- **L12.** `next.config.ts` `remotePatterns` does nothing, because every `<Image>` is `unoptimized`. Either drop `unoptimized` (and get resizing for free on Vercel) or drop the config.
- **L13.** Public `/dogs/[id]` has no `generateMetadata`, so shared dog links show the generic DOGSRUN card. Cheap win for social sharing.
- **L14.** Photo uploads (`new-dog-form.tsx:61`, `edit-form.tsx:84`) use the raw filename in the storage path and have no try/catch around `imageCompression`. A non-image file leaves the form stuck on "Adding Dog…". Admin dog delete leaves orphan photos in storage.
- **L15.** Welcome checklist tells shelters to "go to their profile and trigger an alert", but alerts fire automatically on intake.

## Tooling & process

- **T1. Pre-commit hook partly broken** (`.husky/pre-commit`):
  - The ESLint step checks for `eslint.config.js`, but the repo has `.mjs`, and `--staged` isn't an ESLint flag, so it never runs.
  - The dependency check greps for `"dependencies"` in the diff, so it only fires when the change is within 3 lines of that key.
  - The console check blocks `console.error`, which the API routes legitimately use for server logs.
- **T2. CI runs no tests.** At minimum, add `npx tsx src/lib/matching.test.ts` (no DB, under 1s). Playwright needs a non-prod Supabase project first (see H1).
- **T3. Docs drift — fixed 2026-10-04.** CLAUDE.md (Next version, root layout, design tiers, browser-write exceptions, testing), README, CONTRIBUTING and SOP (matching triggers, digest behavior, Deactivate, email failures) were updated to match the code.
